# 扣子（Coze）部署适配说明

> 目标：本地写好的 Next.js + Drizzle 项目**原样导进扣子编程**，不在云端再改一遍代码。
> 依据：扣子官方文档（链接见每节）。核实时间 2026-10-21。

## 0. 一句话结论

**能适配，而且大部分是平台侧的能力，不需要改代码**。真正需要提前改的只有两处：

1. 数据库连接：从"只有 PGlite"改成"有 `DATABASE_URL`/`COZE_*` 就走真 PostgreSQL"（**已改完**，见 §2）
2. 部署形态：`next.config.ts` 的 `output: "standalone"` 平台不认，需要能 `npm run build` + `npm start`（**已兼容**）

其余（域名、日志、回滚、环境变量隔离、数据库备份）都是平台给好的。

## 1. 平台给的能力（已核实）

### 1.1 生产数据库 = 标准 PostgreSQL

- 扣子编程**内置数据库服务，底层就是 PostgreSQL 引擎**，支持标准 SQL 方言、标准数据类型（int2/int4/int8/numeric/jsonb/timestamptz/vector…）。
  来源：[集成数据库能力](https://docs.coze.cn/guides_integrate_database.md)
- **开发库与生产库物理隔离**，各自独立；不同项目的库也互相隔离。
- 连接凭据（地址/端口/用户名/密码）由平台**自动保存为环境变量**并注入，代码不接触明文。
- 支持秒级自动备份 + 时间点恢复；导出表数据（CSV / SQL）。
- 支持级联删除、`Definition` 查看表结构。

**对我们的意义**：`db/schema.ts`（Drizzle）不用改，SQL 不用改，`db/migrations/*.sql` 可以在开发库里直接执行。

### 1.2 部署 / 发布环境

- 网页应用部署产物 = **动态网站**，通过默认域名（`*.coze.site`）或自定义域名访问。
  来源：[部署运维概述](https://docs.coze.cn/guides_deployment_ops_overview.md)
- 部署流水线自动做三件事：**构建 → 打包 → 部署**，全程有日志。
- 支持**部署历史与一键回滚**、**在线运行日志**、部署前审核（网页应用会审名称/描述/内容）。
- **不需要选服务器**：平台自动分配运行资源，没有配置规格/地域的选项。

### 1.3 环境变量（开发/生产隔离）

- 平台内置**系统环境变量**（`COZE_` 前缀，数据库凭据就走这里）；自定义变量**不能**以 `COZE_` 开头。
- 开发环境变量在 AI 编程环境里配；**生产环境变量只能在「发布管理」页配，改完要重新部署才生效**。
- 首次部署时系统会把开发环境变量同步到部署页，可以逐个调整。
  来源：[管理环境变量](https://docs.coze.cn/guides_environment_variables.md)

### 1.4 数据库在部署时的同步策略（最容易踩坑的一条）

| 阶段 | 行为 |
|---|---|
| **首次部署** | 基于开发库的表结构创建生产库；**可选择是否把开发库的数据一起同步过去** |
| **后续部署** | **只同步表结构（Schema）变更，不同步数据** |

来源：同上「开发与生产环境」表。

**对我们的意义**：学生账号、实验目录这类种子数据，趁首次部署勾选"同步数据"一次性带过去最省事；之后再加数据只能走 SQL 或应用内的管理功能。

### 1.5 导入已有项目（GitHub / 本地 ZIP）

- 支持从 **GitHub 仓库**导入（需完成 GitHub OAuth 授权，仓库名 `owner/repo`），导入后自动绑定仓库。
- 也支持 **本地 ZIP**（≤500MB，不含 `node_modules`），ZIP 导入不会自动绑仓库。
- 导入后编程 AI 会先读代码，可以继续用自然语言迭代、预览、部署。
  来源：[Coze CLI：导入已有项目](https://docs.coze.cn/coze-cli-import-existing-project.md)

### 1.6 Coze CLI（接口化操作，给 Agent 用）

- npm 包 `@coze/cli`，`npm install -g @coze/cli --foreground-scripts`，然后 `coze self skill install` 给 Agent 装技能、`coze auth login --oauth` 登录。
- 能力覆盖：项目全生命周期、代码仓库授权/导入/绑定/推送拉取、**云数据库建表/执行 SQL/导出数据/时间点回滚**、环境变量与自定义域名、预览与部署、部署日志与状态查询、任务取消。
- 输出支持 JSON / 事件流，适合脚本与 Agent 调用。
  来源：[Coze CLI 介绍](https://docs.coze.cn/developer_guides_coze_cli)

> 这正好回答"能不能走接口部署"：**可以**。装 CLI 后，导入仓库、配环境变量、部署、查日志全部能在命令行/Agent 里完成。
> 注意：`@coze/cli` 是字节发布的全局包，本机安装属"引入第三方可执行程序"，需先确认再装（本仓库尚未安装）。

## 2. 我们项目已做的适配（本轮代码）

`lib/db/index.ts` 现在是一个双模入口：

```
DATABASE_URL / COZE_DATABASE_URL / COZE_PG_URL / COZE_POSTGRES_URL / COZE_DB_URL / POSTGRES_URL
        └─ 命中 → postgres.js + drizzle-orm/postgres-js，走真 PostgreSQL
PGHOST/PGUSER/PGPASSWORD/PGDATABASE（或 COZE_PG_* 拆分变量）
        └─ 命中 → 拼成连接串，同上
都不命中 → PGlite（本地开发，行为与之前完全一致）
```

- 依赖只新增了 `postgres`（postgres.js，约 200KB，`prepare: false` 以兼容托管连接池）
- `lib/db/index.ts` 导出 `dbMode`（`"postgres" | "pglite"`），排查时看这一项就能判断当前连的哪种库
- `lib/persist/test-support.ts` 明确只在 PGlite 模式可用（测试环境）
- 验过：`tsc` 0、`vitest` 407 通过（本地仍走 PGlite，行为未变）

**所以导到扣子后不需要再改数据库代码**，只要平台注入了 `DATABASE_URL` 或 `COZE_*` 其中之一。

## 3. 部署前 checklist

### 3.1 仓库侧（本地做）
- [x] 双模数据库入口
- [x] `db/migrations/*.sql` 幂等可重复执行
- [x] 种子脚本 `db/init.mjs` + `db/seed-demo.mjs`（不依赖 PGlite 特有语法）
- [ ] 确认 `next.config.ts` 在平台构建环境下通过（`output: "standalone"` 保留无害，平台会用 `npm run build` + `npm start`）
- [ ] 把 `.env.local.example` 里的变量名与 §2 对齐（只写变量名和示例，不写真实值）

### 3.2 扣子侧（部署时做）
1. **导入项目**：从 GitHub 导入 `sryimnoob123/chem-lab`（或上传 ZIP）
2. **接入数据库**：在项目里开通数据库能力 → 平台创建开发库并注入凭据
3. **建表 + 种子**：在开发库里执行 `db/migrations/0001_init.sql`，再跑种子（让编程 AI 执行 SQL，或用数据库可视化界面导入）
4. **配环境变量**：自定义变量只放业务开关（如教师口令），**不要**放数据库连接串（那是系统变量）
5. **预览验收**：用默认域名预览，跑一遍「登录 → 前测 → 操作 → 报告」
6. **首次部署**：勾选**同步数据**（把开发库的种子带过去），配生产环境变量
7. **线上复验**：学生账号 `20250101 / 周若曦`、教师口令、报告出分、CSV 导出

### 3.3 已知限制（影响我们的点）
| 项 | 限制 | 影响 |
|---|---|---|
| 数据库数量 | 每个项目仅 1 个开发库 + 1 个生产库 | 够用；测试数据别污染开发库 |
| 后续部署 | 只同步 Schema，不同步数据 | 新增种子数据要单独写 SQL 执行 |
| 环境变量 | 生产侧改完必须重新部署 | 改配置=一次部署 |
| 服务器 | 无法选规格/地域 | 性能不可控，只能用日志观察 |
| 审核 | 网页应用部署会审核名称/描述/内容 | 文案避免敏感词 |
| 项目类型 | 网页应用部署成"动态网站"，**不是 API 服务** | 若要给别人调接口，需要另建智能体/工作流项目，或在本项目里自己开 API 路由（我们已有 `/api/*`，但它是站内接口，不对外发 key） |

## 4. 和本地环境的差异对照

| 项 | 本地 | 扣子 |
|---|---|---|
| 数据库 | PGlite（WASM，文件落 `.pgdata`） | 真 PostgreSQL（托管，开发/生产隔离） |
| 连接方式 | `PGLITE_DIR` | 平台注入 `COZE_*` / `DATABASE_URL`（代码已兼容） |
| 种子数据 | `npm run db:init && npm run db:demo` | 开发库执行 SQL / 首次部署勾选同步 |
| 启动 | `node .next/standalone/server.js` | 平台流水线 `npm run build` → `npm start` |
| 域名 | `http://localhost:3001` | `https://<随机>.coze.site` 或自定义域名 |
| 环境变量 | `.env.local` | 平台「发布管理」页 |
| 日志 | `logs/server.log` | 部署管理页在线日志 |
| 回滚 | 手动 | 一键回滚到任意历史版本 |

## 5. 还没确认的唯一不确定项

**平台注入的数据库环境变量具体叫什么名字**。文档只说"以 `COZE_` 为前缀"，没写死是 `COZE_DATABASE_URL` 还是拆开的几段。

处理办法已经内置：§2 的探测逻辑覆盖了 6 种常见整串命名 + 拆开的 `COZE_PG_*` / `PG*`，任一命中即可。
如果部署后发现 `dbMode === "pglite"`（说明一个都没命中），排查步骤：
1. 在扣子「数据库 > 设置」页看平台给的环境变量实际名称
2. 把它加进 `lib/db/index.ts` 的 `candidates` 数组（一行改动）
3. 重新部署
