## 结论先说

上一轮帧率表的三个坑**都定位到了具体帧、改到了根上**，不是加 `will-change` 糊过去的：

1. **C1 那 165ms 不是动画**——是第一次 `new AudioContext()`（开音频设备，本机实测 **59~190ms 同步阻塞**）正好落在"松手投放"那一帧。现在改成「页面空闲时先建 + 手势里只 `resume()`（0.2ms）+ 建好前的声音入队补播」。1440 下 max 帧间隔 **173.7ms → 18.0ms**。
2. **C3+C2 的 97ms / C6 的 5 帧超 33ms**——是"倾倒层卸载 + 动作层挂载 + 步骤推进"在一次提交里叠了两个 React 提交，开发/生产构建下都顶一帧。做了三件事：玻璃器皿 `VesselArt` 上 `memo`（8 台器皿没必要跟着重渲染）、`vesselShift` 用 `useMemo` 稳定引用（否则 memo 永不命中）、倾倒结束接下一拍动作拆到下一个任务。生产构建下六套动画 **0 帧 >33ms**。
3. **C6 定容 2.0 秒 → 1.67 秒**：beats 1920 → 1600，**一拍没删**（滴管进出 / 三滴 / 液面涨 / 涟漪 / 悬滴 / 摇匀全在），只收紧 delay 与时长。

四绿 + E1 全链 8/8 全过；四页像素回归比上一轮**持平或更好**（0.000% / 0.000% / 0.000% / 0.0035%）。

## 六、这一轮新踩的坑（别再踩）

1. **`new AudioContext()` 是 60~190ms 的主线程阻塞**，而且第一次一定发生在某个用户手势里（自动播放策略）。别在手势回调里同步建 —— 会直接顶掉动画第一帧。
   正确姿势：页面挂载后 `requestIdleCallback` 里先建（构造出来是 suspended 也无所谓），手势里只 `resume()`（0.2ms）。
2. **`React.memo` 在 props 里有"每次渲染都新建的数组/对象"时永远不命中**。`shiftInsideRight()` 每次都返回新数组，所以 `VesselArt` 一开始 memo 是白做的；先把 `vesselShift` 用 `useMemo` 稳定住才生效。
3. **PGlite 被强杀会坏**：本轮踩了 3 次 `RuntimeError: Aborted()`（页面数据全空、`/api/*` 500，但页面靠兜底渲染，很像业务 bug）。重建即可：停服务 → `npm run db:init && npm run db:demo`。**`npm run build` 会把 `.next` 写坏 dev 的 HMR 状态**，跑完 build 必须重启 dev。
4. **playwright 起来会占用 3000 并在结束后关掉它**；用它跑 e2e 之后再跑自定义证据脚本，记得重新起 dev。
5. **`/plan` 的三种结果剧场只在「设计态」渲染**：必须点主题 → 等 4 段拆解 → 点「开始设计方案」才出现，且「危险」那条是 17 拍、约 20~30 秒才出结论（截图脚本里要轮询"正在演"消失）。
